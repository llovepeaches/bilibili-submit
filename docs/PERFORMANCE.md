# 客户端卡顿排查与优化报告

本文回答四个问题：**为什么会卡**、**什么场景下卡**、**改了什么**、
**改完快了多少**。所有数字都来自 `tools/bench_ui.py`，可随时复现：

```bash
xvfb-run -a python3 tools/bench_ui.py
```

脚本把「优化前」和「优化后」两种写法放在同一份文件里，一次运行同时跑出
两组数字，不存在「两次测量环境不同」的问题。

---

## 一、结论先行

卡顿**不是**网络请求阻塞主线程，也**不是**内存无上限增长。真正在主线程
上烧时间的是四段**重复重排**——Tk 每写一次控件就要重排一遍，而这些重排
里有绝大部分是在重画一模一样的内容。

| 热点 | 触发场景 | 优化前 | 优化后 | 提速 |
| --- | --- | --- | --- | --- |
| 日志写入 | 上传 / 批量投稿，进度成批到达 | 74–77 ms / 1000 行 | 2.7 ms | **27×** |
| 列宽重算 | 拖窗口边框、切页面 | 6.2–6.6 ms / 300 次 | 0.1–0.2 ms | **41–45×** |
| 汇总刷新 | 批量投稿每行开始 / 结束 | 13.4–13.7 ms / 100 次 | 6.6–6.8 ms | **2×** |
| 历史页切页 | 每次切到「历史」页 | 1794–1800 ms / 1000 次 | 1.7–1.8 ms | **约 1000×** |
| **合计** | | **约 1892 ms** | **约 11.4 ms** | **约 165×** |

> 合计被最后一项主导。去掉它，前三项合计 94 → 9.7 ms，约 **10×**。
> 每项跑 3 遍取最快（Xvfb 上抖动来自同机其它负载，只会让某次变慢，
> 不会让任何一次变快），区间是连续两次运行的取值范围。

---

## 二、四个热点逐个拆

### ① 日志写入 —— 真凶是 `Text.see()`

**场景与触发条件**：上传单个大文件、批量投几十上百个任务。进度回调是
**成批到达**的（分片上传每片一条、每个任务开始/结束各一条），一次投稿
轻松上千行。

**定位过程**：把 2000 行的写入按操作拆开分别计时——

| 写法 | 耗时 |
| --- | --- |
| 现行（每行 configure + insert + see） | 175.7 ms |
| 去掉 see | 13.6 ms |
| 只 insert | 1.8 ms |
| 只 see | 1.2 ms |
| 只 configure ×2 | 10.4 ms |
| **批量一次 insert + 一次 see** | **0.8 ms** |

`see()` 每次都要让 Text **重排一遍再算滚动位置**，行数越多越贵，写一行
触发一次——占了写入耗时的 **94%**。

**改法**（`ui/widgets.py` 的 `LogConsole`）：

- `insert` 保持同步（测试和用户都要立刻读到内容），`see` 用 `after_idle`
  合并——一帧里来多少行都只滚一次；
- 新增 `extend()`，成批到达的日志合并成一次 `insert`；
- 新增 `MAX_LINES = 3000`，超出的从顶部丢弃。

**效果**：74–77 → 2.7 ms（约 27×）。封顶后写满 10000 行仍稳定在
3.8 ms/1000 行，不再随行数线性变慢（实测第 3000 行后走平）。

### ② 列宽重算 —— docstring 承诺了，代码没做

**场景与触发条件**：拖窗口边框、切换页面、任何一次布局变动。
`<Configure>` 在布局的**每一步**都会往表格派发一次，切一页能派发上百个。

**证据**：`views/tasks_table.py:207` 的 docstring 写着「只在宽度真的变了
时动手」，但函数体里**没有宽度缓存**——每个 Configure 都执行 7 次
`self.tree.column(...)`。`views/history.py` 同样问题（3 列）。
对照 `app.py:309` 的 root 级 `<Configure>` 处理，那里四道闸门齐全——
**主窗口有守卫，两个表格漏了**。

**改法**：列宽只由总宽决定，所以缓存总宽就等于缓存了全部列。宽度没变时
一次 `column()` 都不调。

**效果**：6.2–6.6 → 0.1–0.2 ms（41–45×）。同时补测了「宽度真的每步都变」
的情况（真在拖边框的那一段）：约 6.0 ms，与优化前同量级——说明优化只是
挡掉了重复，**没有把活推到别处**。

### ③ 汇总刷新 —— 全表扫了三遍

**场景与触发条件**：批量投稿时，每个任务开始和结束各刷一次「已选 /
成功 / 失败」计数。几百个任务时这段是最密的循环。

**改法**：

- `_update_summary` 从「`get_children` 三遍 + 两次列表推导 + 两次 `count`
  （共 6 遍全表）」改为**单次遍历**累加；
- 删掉 `on_progress` 里的一次重复全表刷新——`mark()` 内部已通过
  `on_changed` 通知过，每个 Event 少扫一遍全表。

**效果**：13.4–13.7 → 6.6–6.8 ms（2×）。这一项绝对值不大，但它是批量
执行里**频率最高**的那段，省下来的是「每个任务 ×2 次」。

### ④ 历史页切页 —— 每次切换都重建整张表

**场景与触发条件**：投稿中途点去「历史」看一眼再点回来。主窗口
`App.show()` 每次切页都会调 `view.refresh()`。

**证据**：历史文件是**追加写**的，投得越多越大。切一次页要把整个 JSON
读进来 parse 一遍，再删掉、插回 200 行 Treeview——**而内容与上次完全
一样**。

**改法**：先比对文件指纹（`mtime_ns` + 字节数），没变就不动。历史只有
投稿成功那一刻才会变，所以 1000 次切页里只该重建一次。「刷新」按钮走
`refresh(force=True)`，仍然真的重读。

**效果**：1000 次切页 1794–1800 → 1.7–1.8 ms。

## 三、已排除的两个常见嫌疑

这两条是用户最可能猜的方向，实测都不是主因——写在这里是为了避免以后
重复排查。

**网络请求阻塞主线程？** 不是。扫描目录（`_scan_to_tasks`）、ffmpeg
定位、视频元信息探测（`_probe_meta`）、更新检查、上传全程都跑在
`Worker` 工作线程上，回主线程只做回调，并且带**代次（generation）防
过期**——连续换两个文件时，慢的那次晚回来不会覆盖新文件的结果。
上传时界面变慢是日志/汇总的**重绘成本**，不是网络。

**内存无上限增长？** 不算是。日志封顶前实测累积效应：写第 1–1000 行
2.8 ms，第 9001–10000 行 3.8 ms，只慢 1.33×，且第 3000 行之后就走平了。
所以 `MAX_LINES` 的定位是**兜底**（防止极端长批次把内存吃下去），不是
主要提速点。

## 四、怎么验证

```bash
# 1. 数字：新旧写法同脚本对比，一次跑出两组
xvfb-run -a python3 tools/bench_ui.py

# 2. 防回退：8 条守卫，每条都做过变异自检（撤掉优化必红）
xvfb-run -a python3 -m pytest -q tests/test_ui_perf.py

# 3. 全量回归
xvfb-run -a python3 -m pytest -q          # 647 passed
python3 -m pylama --max-complexity 20 bilibili_submit tests tools
```

`tests/test_ui_perf.py` 里每条断言的注释都写明「撤掉优化会怎样」，
并且对四处改动逐一做过变异验证：

| 撤掉的东西 | 会红的用例 |
| --- | --- |
| 列宽宽度缓存 | `test_resize_columns_does_nothing_when_the_width_has_not_moved` |
| 日志 `MAX_LINES` 上限 | `test_log_console_caps_the_line_count` |
| 滚动 `after_idle` 合并 | `test_log_console_defers_the_scroll_...` |
| 历史页指纹比对 | `test_history_refresh_skips_rebuild_when_file_unchanged` |

另外两条反向守卫，挡的是「优化挡过头」：宽度真的变了必须重算
（`test_resize_columns_still_recomputes_when_the_width_moves`），
文件真的变了必须重建、`force=True` 必须重读。
